# GAME_DESIGN.md — "Клумба: цветочная головоломка"

Short name: **"Клумба"**. Working title "Garden" in code/repo. A browser logic puzzle game for Yandex Games.

## Theme

A cozy garden. Each colored region of the grid is a flower bed; the player plants exactly one flower per bed. Mascot: a small ladybug who gives hints (placeholder, drawn with SVG for now).

## Rules

An N×N grid is divided into N colored regions ("flower beds"). The player places flowers so that:

- each region contains exactly one flower;
- each row contains exactly one flower;
- each column contains exactly one flower;
- flowers never touch each other, not even diagonally (no two flowers in adjacent cells, including diagonal neighbors).

## Controls

- Single tap on an empty cell → white X mark ("no flower here"), placed immediately, no delay.
- Double tap (a second tap within ~300 ms on the same cell, while it shows an X) → the X becomes a flower.
- Single tap on an X with no quick follow-up → clears back to empty.
- The pre-placed flower, any correctly planted flower, and any red X marks all lock immediately and can't be changed — tapping or dragging over them does nothing.

A flower always needs a deliberate double tap; a single tap never plants one directly. Works the same with mouse and touch, and `touch-action: none` on the board plus a non-zoomable viewport keep a fast double-tap from triggering the browser's zoom gesture, and keep the page from scrolling while dragging on the board.

**iOS double-tap-zoom fix.** On iOS Safari-engine browsers (including third-party WKWebView wrappers like Yandex Browser on iOS), `touch-action` and a non-zoomable viewport meta tag alone are not reliably enough to stop the native double-tap-to-zoom gesture - a long-standing WebKit quirk - so double-tapping to plant a piece could also zoom the whole page. Four layers, none of which touch gameplay:
- **CSS** (one small isolated block at the very top of `css/style.css`): `touch-action: manipulation` on `html`/`body`/`#app`/`.screen` - the effective minimum for every descendant via the touch-action ancestor-intersection rule, so it covers the board's frame/gap padding, the top bar, rules cards, helper buttons, the menu, the loading screen, and every overlay, not just `.board`/`.cell`'s own stronger `touch-action: none`, kept as-is. Plus `-webkit-touch-callout`/`-webkit-user-select: none` on the board, every button, and every overlay (no stray long-press callout or text selection).
- **Pinch-zoom guard** (`js/zoomguard.js`, wired by `js/main.js`): document-level, non-passive `gesturestart`/`gesturechange`/`gestureend` listeners (WebKit-only events) that block pinch-zoom inside the loading, menu, game, and tutorial screens, while deliberately leaving the settings/check-in/win/fail overlays pinch-zoomable for low-vision players.
- **Double-tap guard** (`js/zoomguard.js`): a document-level, **capture-phase**, non-passive `touchend` listener that cancels only the *second* touchend's default when it lands on the same cell/button within ~350ms, inside those same four screens only - it never touches a text input or a scrollable popup, and it only ever calls `preventDefault()` on the event it's handed, never any game logic. The board's/tutorial's own tap/drag/double-tap-to-plant logic is entirely pointer-event-driven (`js/input.js`, `js/tutorial.js`) and has already reacted to the gesture by the time `touchend` fires, so it's unaffected whether or not this guard also runs.
- **Safe zoom reset** (`js/main.js`, no visible UI): if `visualViewport.scale` is still `> 1` when entering a new screen (e.g. the player pinched inside a popup), the viewport meta tag's `content` is re-asserted (nudges WebKit back to its initial scale) and the page is scrolled back to `(0, 0)`.

The viewport meta tag stays `width=device-width, initial-scale=1, maximum-scale=1, user-scalable=no, viewport-fit=cover`.

**Drag to mark.** Press and drag across cells to mark or clear several at once: if the drag starts on an empty cell, every empty cell it passes gets a white X; if it starts on a white X, every white X it passes is cleared. Flowers, the pre-placed flower, and red X marks are never touched by a drag — the drag just passes over them. A drag never triggers the double-tap flower placement, regardless of how it moves.

## Level start types

Every level's start set (what's already on the board when it begins) is decided by a deterministic "start type", computed by `js/levelstart.js` from the level number alone - the generated beds and the one true solution (`js/generator.js`/`js/state.js`'s `buildLevel`) never change, only what's pre-placed on top of them.

- **gift** - exactly one solution flower pre-placed and locked (the original, only, behavior). Levels 1-9 always get this (tutorial-like).
- **none** - nothing pre-placed; the hardest start.
- **rich** - 0 pre-placed flowers, plus 8-12 white crosses pre-placed on cells that are guaranteed **not** part of the solution; a friendly, generous start, always used on milestone levels (see below), without ever exceeding the 1-gingerbread-per-level cap below.
- **notes** - 0-1 solution flowers pre-placed, plus 5-10 white crosses pre-placed on cells that are guaranteed **not** part of the solution (so they're always true information) - fewer crosses if fewer eligible cells exist.

**At most 1 pre-placed gingerbread per level, every level, including milestones.** `gift` gives its usual 1; `none` and `rich` give 0; `notes` keeps its 0-1 roll. `rich` used to pre-place 2-3 flowers, which could stack with other rewards to feel over-generous and - worse - meant a single level could start more than half-solved; it now expresses its generosity entirely through crosses instead. `tests/generator-caps.test.js` scans levels 1-200 and asserts this cap directly.

**Schedule** (`Garden.levelstart.startTypeForLevel(level)`, one pure function of the level number):
- Levels 1-9: always `gift`.
- From level 10: every multiple of 10 (10, 20, 30, ...) is a **milestone** level - its start type is always `rich`; every *other* multiple of 5 (15, 25, 35, ...) is `none`; every remaining level picks among `gift`/`rich`/`notes` via a dedicated seeded PRNG roll.
- "Milestone" (`data-level-kind="milestone"`, see Status UI below) and "start type" are independent - a level can roll `rich` on its own without being a milestone.

**Determinism and isolation from generation.** All of the start-type schedule's random choices (the type roll itself, how many flowers, which ones, how many crosses, which ones) are drawn from one dedicated PRNG stream seeded via `Garden.levelstart.levelStartSeed(level)` (`js/rng.js`'s `createRng`) - a transform deliberately distinct from both `buildLevel`'s plain level-number seed and the Random helper's `randomRollSeed`, and this stream is created *after* generation already finished and never shared with it, so beds and the solution stay bit-for-bit identical to before this feature existed (`tests/levelstart.test.js` builds a sample of levels 1-80 both ways and diffs them directly). Pre-placed pieces/crosses are locked, earn no points, and (exactly like the original single pre-placed flower) are never added to `awardedCells`; the lowest-row Finder target and the Random/Snowman cross-eligibility rules already skip any locked/given cell, so Finder, Random, Snowman, and the win-fill wave all keep working unchanged whether a level starts with 0, 1, 2, or 3 given flowers. The menu's "Продолжить" detection (`js/menu.js`'s `hasProgress`) now requires an X mark to be *unlocked* to count as player progress, specifically so a `notes`-type level's pre-placed (locked) crosses are never mistaken for something the player did.

**Milestone reward.** On a milestone level's first-ever completion (reusing the exact same `loadBestTime`-based guard that already protects the total score), the player is granted +1 charge of **each** helper through `Garden.helpers.addCharges` - never a direct storage write - with the same persist-before-credit order the daily check-in uses (the level's best time is saved, marking it "completed", before charges are credited), so a replay of an already-completed milestone level never re-grants it. Shown on the win screen as a short "+1" per helper (reusing the daily check-in's reward-badge markup/animation, so Reduce Motion is honored for free). No coins, seeds, prices, or invented statistics.

**Design hooks** (logic/markup only - visual styling is a separate pass): the board wrapper carries `data-start-type="gift|none|rich|notes"` and `data-level-kind="normal|milestone"`; every pre-placed cell (piece or cross) carries `data-given="true"`; a milestone banner (`#milestoneBanner`, with a single `#milestoneBannerTitle` text span, "Праздничный уровень!"/"Festive level!" via i18n) is shown for the whole time a milestone level is open and hidden otherwise - it used to also show a second, redundant `#milestoneBannerCaption` line ("Особый уровень"/"A special level"); that element is still in the markup but is now always left empty/hidden by `js/render.js` rather than populated, collapsing the banner to one short phrase (**a visual hook for Codex**: the now-always-empty caption span/its spacing could be removed or restyled). The win screen's `#milestoneRewardBadge` shows the helper-charge reward.

## Mistake feedback

If the player plants a flower in a cell that breaks a rule or isn't part of the level's one true solution, that cell gets a red X (visually distinct from the plain white "no flower" X) with a short shake, one candy-cane life pops/fades away, and the cell locks — the red X stays as a permanent marker that no flower belongs there.

## Level-complete fill

The instant the last correct flower is planted, every remaining empty cell on the board gets a white X in a quick staggered wave (each cell appearing ~35ms after the last), and only once that wave finishes does the win screen appear. A solved board is never left with ambiguous empty cells.

## Level generator

1. Place N flowers on an N×N grid satisfying all rules (one per row/column, no touching).
2. Grow colored regions outward from each flower to partition the grid into N connected regions.
3. Run a solver against the generated puzzle (regions only, flower positions hidden) to verify the solution is unique.
4. If not unique, regenerate.

Grid size by level: 1-2 → 4×4, 3-5 → 5×5, 6-9 → 6×6, 10-14 → 7×7, 15+ → 8×8 (the cap). Every level has at most one pre-placed, locked flower regardless of size (see Level start types above - some start types pre-place zero).

8×8 generation is verified fast: across levels 15-74 the slowest observed build was ~74ms, far under the 1-second budget, so no precomputation/caching was needed. `tests/progression-speed.test.js` guards this (fails if any 8×8 build in a 60-level sample takes ≥1000ms) and also locks in the exact size-per-level table above.

**Single-cell flower-bed regions.** A region that ends up just 1 cell is allowed freely on levels 1-5 (it can help onboarding). From level 6 on, a board may have **at most 1** such region, and only on a level that's a multiple of 4 (`Garden.state.singleCellRegionCap(level)`, deterministic by level number, never a separate random roll) - every other level must have **zero** (every region needs 2+ cells). Enforced by `Garden.generator.generateLevel`'s 4th parameter (`maxSingleCellRegions`): after growing regions, if more single-cell regions exist than the cap allows, `repairSingleCellRegions` first tries to patch it up by stealing one cell for the lone region from an adjacent region (never the donor's own seed/flower cell, and only if the donor keeps 2+ cells and stays itself connected) before falling back to rejecting the whole attempt and retrying, exactly like the existing uniqueness check. Rejecting immediately by forcing every region to start at 2+ cells was tried first and measured a ~1-in-15000 chance of the result still having a unique 8×8 solution (a single-cell region turns out to often be exactly what pins an 8×8 board down to one true solution) - patching up only the rare case that actually needs it instead keeps that at ~1-in-600, well inside the 1-second budget (worst case observed: ~400ms). `tests/generator-caps.test.js` scans levels 1-200 and asserts both this cap and the gingerbread cap above hold everywhere, including on milestones, without breaking uniqueness.

**Deterministic by level.** Every random choice in generation (flower placement, region growth, which solution flower is pre-placed) is drawn from a seeded PRNG (`js/rng.js`, mulberry32) seeded by the level number itself — never `Math.random`. Level N therefore looks exactly the same — same beds, same colors, same pre-placed flower — for every player, every time, every reload. `tests/determinism.test.js` builds each of a sample of levels twice and asserts the results are identical.

## Level timer

`elapsedSeconds` (used for the star rating and best time) only counts **active play time** - `js/state.js`'s `pauseTimer(reason)`/`resumeTimer(reason)` track a set of overlapping pause reasons (the clock only actually resumes once every reason has cleared), wired up in `js/main.js`/`js/input.js` to: `document.visibilitychange` (tab hidden/visible), `pagehide`/`pageshow`, `blur`/`focus`, and Settings or "How to play" being open. There is no idle timeout - an uninterrupted, visible session keeps counting no matter how long it runs; pausing only ever happens through one of those explicit triggers. `tests/timer-pause.test.js` covers this with a monkey-patched clock (baseline active time, a hidden-tab stretch excluded, overlapping pause reasons, an overlay-open stretch excluded, and a long idle-but-visible stretch still counted in full).

**Best-time migration.** Best times recorded before this fix could be inflated by time spent hidden/backgrounded. `platform.js` bumps `BEST_TIME_SCHEMA_VERSION` (now 2) and runs `migrateBestTimes()` once, automatically, the moment the module loads: if the stored schema version is older, every `garden.bestTime.*` key (tracked via a small `garden.bestTimeLevels` index, since `saveBestTime` now maintains it) is wiped and the version bumped - idempotent, so it only ever wipes once per player. Progress, total score, in-progress board state, and helper charges are completely untouched. Covered by `tests/timer-pause.test.js`.

## Saving in-progress play

The current board (every cell's X/flower/red-X mark and lock state), remaining lives, and the level's running score are saved to localStorage after every move, keyed by level number. Reloading mid-level restores exactly where the player left off. The saved board is cleared when the level is completed (solved) or explicitly restarted (Retry); a level never resumes stale progress after either of those.

## Rules bar

Above the board, three small cards each show a tiny 3×3 diagram (CSS/SVG) next to a short rule reminder, all text through i18n:

- **"1 flower per bed"** — a flower in the center cell; the top row and left column cells (same bed color) show X; the remaining cells are neutral.
- **"1 flower per row and column"** — a flower in the top-middle cell; X on the other two top-row cells and on the two cells below it in the middle column; the rest neutral.
- **"Flowers can't touch"** — a flower in the center cell; X on all 8 surrounding cells.

On levels 1-5 (inline mode) the bar's horizontal padding matches the board's own side padding, and the three cards share that width equally (`flex: 1 1 0; min-width: 0`) rather than each claiming a fixed width, so the row can never grow wider than the viewport — the rule text wraps onto a second line instead, while the mini 3×3 diagrams stay full-size. The level-6+ popup mode is unaffected.

## Bed tracker

A row above the board shows one small icon per flower bed, colored to match that bed, in a fixed left-to-right order (by bed index). Once a bed has its correct flower, its icon shows a small flower; otherwise it stays a plain colored swatch.

## Feedback and scoring

- Planting a flower correctly earns 10 points: a floating "+10" pops up near that cell and fades out, and the score display updates immediately. The cell locks the instant it's correct (see Controls above), so it can never be re-earned within the same attempt — and as a belt-and-suspenders safeguard, each cell's points are tracked as "awarded" in the saved board state too, so even a hypothetical future bug that unlocked a cell couldn't double-award it.
- Score is tracked two ways: the current level's score (resets each attempt, saved/restored with the board so a reload mid-level doesn't lose it), and the running total across the whole game. The total only ever gains a level's points once — on that level's first-ever completion — so retrying or somehow replaying an already-completed level never inflates it (best time and star rating can still improve on a replay, just not the total score). While playing, the displayed total previews the current level's in-progress score on top of the real banked total; once won, it shows the real banked total exactly.
- Finishing a level with no mistakes shows a big animated "Perfect!"; finishing after at least one mistake shows "Done!" instead — either way the level's score earned is shown alongside it.

## Win screen rating

No fake "you beat N% of players" claims anywhere — that kind of stat only appears once it can be real (see Roadmap step 8). Instead, the win screen shows:

- **1-3 stars**, computed from mistakes made and time taken this level: 3 stars needs zero mistakes and finishing within `gridSize × 10` seconds; 2 stars needs at most one mistake and finishing within `gridSize × 20` seconds; otherwise 1 star. Stars pop in with a short staggered animation.
- **A rank title**, shown via `RANK_KEY_BY_RATING` in `js/render.js`: 1 star → "Пряничный новичок" ("Gingerbread rookie"), 2 stars → "Пряничный мастер" ("Gingerbread expert"), 3 stars → "Пряничный волшебник" ("Gingerbread wizard").
- **Best time for the level**, persisted per level in localStorage and updated whenever a run beats it (see Level timer below for what "time" counts).

**Headline vs. stars - known inconsistency, not yet changed.** The "Idealno!"/"Perfect!" vs. "Gotovo!"/"Done!" headline is driven by `snapshot.perfect` (`lives === MAX_LIVES`, i.e. zero mistakes made), completely independent of the star rating, which also factors in elapsed time (`computeRating`). A slow-but-mistake-free run can therefore show "Idealno!" next to only 1 star - the headline says "flawless," the stars say "slow." Proposed fix (not applied, pending confirmation): drive the headline off `rating === 3` instead of `perfect` - "Idealno!" only when all 3 stars are earned, "Gotovo!" for 1 or 2 stars - so the headline and stars always agree, without changing any star threshold.

## Win streak and total stars

**Win streak** (`js/state.js`'s `finishLevel`/`attemptFlower`, persisted via `platform.saveWinStreak`/`loadWinStreak`, a plain counter - not date-based, so it needs no migration and is never touched by leaving/returning to the menu): the number of levels won in a row.

- **Only broken by losing** (all 3 lives spent) - never by leaving a level and coming back (a fresh `State.createGame()` for the same saved progress never touches it), and never by the passage of time (it isn't tied to calendar dates at all, unlike the daily gift).
- **Only a win that represents genuine new progress extends it** - re-winning an already-completed level (the exact same `loadBestTime`-based `alreadyCompletedBefore` guard that already protects the total score and the milestone reward) neither extends nor resets the streak, so it can't be farmed for free bonus charges by replaying the same level. The game currently has no level-select, but a level *can* be replayed today: winning it, then returning to the menu before pressing "Следующий уровень" and pressing "Играть"/"Продолжить" again resumes the same (now-cleared) board fresh. This exception is exactly what keeps that path from being exploitable.
- **A loss always resets it to 0**, with no equivalent exception for an already-completed level - losing on a replay still resets the streak, same as any other loss (stated plainly in the spec as "broken ONLY by losing a level," with no carve-out the way the win-counting rule has one).
- **Bonus every `WIN_STREAK_BONUS_INTERVAL`-th win (5, 10, 15, ...):** `WIN_STREAK_BONUS_AMOUNT` (1) charge of whichever eligible helper the player currently has the **fewest** charges of - ties favor finder, and Snowman is excluded from the eligible set entirely while locked (below level 10), mirroring the exact "fewest charges, tie to finder, Snowman only if unlocked" rule `Garden.checkin` uses for its own day-4/day-7 rewards (kept as a small local copy, `pickStreakBonusHelper`, rather than a cross-module call, since state.js has no other reason to depend on the daily-gift feature). Credited through `Garden.helpers.addCharges` - never a direct storage write. There is no charge cap anywhere in the game today, so "respect any existing charge cap" is currently a no-op (moot, same as the daily gift's note on this); `addCharges` is the one place a future cap would need to clamp. The bonus is granted inside the same once-per-genuine-win `finishLevel` call the streak increment itself lives in, so it's exactly as idempotent as the streak (a reload or double-tap can never grant it twice - see the daily gift's own write-up of why this architecture already prevents double-firing).
- **Shown on the win screen from the 2nd consecutive win on**: "Серия: N" (`.win-streak`) plus a hint of how many wins remain until the next bonus (`.win-streak-hint`, "Побед до бонуса: N"). When a bonus was actually granted this win, `.win-streak-bonus` shows the credited helper's icon and "+1" (same `.reward-badge`/`helper-reward-icons` markup pattern the milestone reward already uses, so it's a one-shot `reward-pop` animation that honors Reduce Motion for free). None of this appears at all on a replay of an already-completed level (nothing to show - no streak change happened) nor is anything special shown on the **lose screen** beyond what already exists there.

**Total stars** (`js/platform.js`): the sum of the best (1-3) star rating ever earned per level, across every level, shown on the main menu. `saveBestStars(level, stars)` is a dumb writer (same convention as `saveBestTime` - the caller in `finishLevel` computes `Math.max(previousBest, rating)` itself) that also keeps a running `totalStars` counter in sync by the exact delta, so the menu never has to re-sum every level's best stars itself; best stars, like best time, can always improve on a replay. **Schema/migration:** per-level star ratings were never recorded before this feature, so there is no historical data to recover - no fabricated/guessed star counts are backfilled for levels already completed before this shipped (consistent with "no invented statistics"). `migrateStars()` (versioned via `garden.starsSchemaVersion`, idempotent like `migrateBestTimes`) just establishes `totalStars` at 0 once; it starts growing from whatever is won *after* this ships. Progress, total score, best times, and helper charges are a completely separate storage prefix and are never touched.

**Design hooks for Codex** (functional only - no styling done here). Unlike the daily gift, there was no existing markup to repurpose for either of these, so the elements are created once in JS and inserted into the existing cards, never replacing or hiding anything already there:
- Win screen (`js/render.js`, inserted into the existing `#winOverlay` card right before the "next level" button): `<p class="win-streak">`, `<p class="win-streak-hint">`, and `<div class="reward-badge win-streak-bonus">` (hidden unless a bonus was granted this win) containing a `helper-reward-icons` span and an amount span, plus an `aria-label` on the bonus badge naming the helper and amount.
- Menu (`js/menu.js`, inserted right after the subtitle, before the menu buttons): `<p class="menu-total-stars">` ("★ N"), with an `aria-label` spelling out "Всего звёзд: N".

## Lives

- 3 lives per level, shown as candy canes (drawn in SVG) instead of hearts. The fail screen title and the lives aria-label ("Осталось N леденцов/леденца/леденец" - `I18n.pluralRu` picks the correct Russian plural form) use "леденцы" ("candy canes"); the old "капли"/"water drops" wording is gone from every JS string (`js/i18n.js`).
- A life is lost when a flower is placed in a cell that breaks a rule or isn't part of the unique solution (see Mistake feedback above).

## Helpers

Three helper tools, each with its own charge count - there is no seed/coin currency
anywhere in the game. Ids: `finder`, `random`, `snowman`.

- **Finder:** plants exactly one correct piece - the solution's lowest-row unplanted
  cell (the same deterministic target the earlier hint system used: the solution list
  is already ordered ascending by row by construction, see `buildLevel`/`generator.js`,
  so this is a plain forward scan for the first cell that isn't already a flower).
  Locked immediately, with the normal bloom/bed-tracker update, triggering the win
  flow if it's the last piece. Worth 0 points, costs no life, is not a mistake, and
  never changes "Perfect!"/"Done!" or the star rating; the cell is still added to
  `awardedCells` as the same belt-and-suspenders guard against ever double-scoring it
  later. Available from level 1.
- **Random helper:** one use rolls a 50/50 outcome: half the time it acts exactly like
  Finder; the other half it places 4 or 5 white X marks (see Crosses below) instead.
  The roll is deterministic and can never be re-rolled by a reload or Retry: it comes
  from a dedicated seeded PRNG stream (`js/rng.js`'s `createRng`, **never** the
  level-generation RNG from `buildLevel`) seeded from the level number plus a
  per-attempt use counter that is persisted with the in-progress board state (reset to
  0 on a fresh attempt/Retry, exactly like the rest of the board). Available from
  level 1.
- **Snowman:** places up to 3 white X marks (see Crosses below), spread across the
  whole board rather than the first few cells in row order - `Garden.state.pickSpreadCrossCells`
  prefers cells in different rows, different columns, and different bed regions, and
  never adjacent to another cross it just chose (including diagonally), using true
  randomness (`Math.random`, deliberately **not** the seeded level-generation RNG or
  Random's deterministic stream - Snowman is meant to feel genuinely random from use
  to use). If too few eligible cells satisfy the full combination, those preferences
  are relaxed one at a time (region, then column, then row, then adjacency last)
  until 3 cells are found or the eligible pool runs out. Locked until the
  player has reached level 10 - checked against the **highest level ever reached**
  (`platform.saveHighestLevel`/`loadHighestLevel`, updated whenever a level starts
  with a number higher than anything seen before), not the level currently open, so
  the lock can never flicker back on by revisiting an earlier level. The locked button
  shows a lock icon and "Lv.10" instead of its charge badge.
- **Crosses** (Random's X-mark outcome, and all of Snowman): only ever land on cells
  that are empty, unmarked, unlocked, **and not part of the level's solution** - they
  are ordinary white X marks, exactly as if the player had tapped them (tapping one
  still clears it, same as always). If fewer eligible cells exist than the helper
  wants to place, it places as many as exist; if none exist, the helper does nothing
  and spends **no** charge (a no-op tap - this can happen late in a level, once most
  non-solution cells are already marked or locked).

### Charges

- 5 charges per helper, granted once on first-ever launch (never re-granted just
  because a balance later drops to 0 - the same grant-once rule the old starting seed
  balance used). Stored and managed by a dedicated module, `js/helpers.js` -
  `getCharges(id)`, `addCharges(id, n)`, `spendCharge(id)` - backed by `platform.js`
  storage (corruption-tolerant; a charge count can never go negative). `STARTING_CHARGES`
  (5) and `SNOWMAN_UNLOCK_LEVEL` (10) are the two constants that live in one place
  (`js/helpers.js`) if either ever needs to change. `addCharges` is also the one credit
  path every charge reward uses, regardless of source: the daily check-in (below) and
  the milestone reward (see Level start types above) both call it directly, never a
  storage write of their own.
- **Spend order:** a charge is deducted and persisted, and (for Random) the use
  counter is advanced and persisted, *before* the board changes - so an interruption
  can never leave a charge spent with no visible effect having actually happened,
  the same discipline the old hint cost used.
- **Double-spend guard:** each helper has its own short lock window (400ms) after a
  successful use that rejects an immediately-repeated tap, so one tap can never spend
  two charges of the same helper - mirrors the old hint's lock window, just per-helper
  now instead of global.
- **No refunds:** Retry never refunds charges already spent this attempt (same rule
  hints followed before); it does reset the per-attempt Random use counter, since
  Retry starts a brand new attempt.
- **Eligibility:** a helper button is disabled whenever it's locked (Snowman only,
  below level 10), at 0 charges, the level isn't in the "playing" state (solved,
  failed, or the win-fill wave still running), or - Snowman only, since its placement
  is fully deterministic and cheap to check in advance - there is currently no
  eligible cross cell anywhere on the board. Random's button stays enabled even when
  a roll could land on a cross outcome with zero eligible cells at that instant - see
  Crosses above for what happens then.
- Helpers never affect score, lives, mistakes, the star rating, or level-generation
  determinism (reloading, retrying, or using every helper available never changes
  what level N looks like or its one true solution).
- Not available in the separate first-launch tutorial (fixed hand-made board, no
  helper buttons in its markup at all - same as the old hint button before it).

### UI

- A row of three round helper buttons below the board (each ≥44px, for touch),
  replacing the old single hint button. Each shows a charge-count badge in the
  corner; at 0 charges it gets a dimmed "disabled" look; Snowman below level 10 shows
  a lock icon and "Lv.10" instead.
- **Icons come from the theme registry.** `Garden.render.helperIconFor(id)` asks the
  active theme's `helperIconSvg(id)` (`js/themes.js`) for real art first; if the theme
  has none for that id (returns `null`, or doesn't implement the function), it falls

  Reduce motion shortens the Finder/Random-finder-outcome bloom to the same plain

## Daily gift

A 7-day reward cycle (`js/checkin.js`, namespace `Garden.checkin` kept for continuity - this replaced the earlier streak-based "Daily check-in" entirely, not alongside it). "Today" is always the player's LOCAL calendar date, derived from local date parts (`getFullYear`/`getMonth`/`getDate`), never a UTC view of the clock.

- **Rewards by cycle position** (`ROTATION_HELPER_BY_DAY`/`DAY4_AMOUNT`/`DAY7_AMOUNT` in `js/checkin.js`, the one place these values live):
  - Days 1, 2, 3, 5, 6: 1 charge each, by a fixed rotation - finder, random, snowman, finder, random.
  - Day 4: 3 charges of whichever of finder/random/snowman the player had the **fewest** charges of *when the current cycle started* (ties favor finder) - see "frozen plan" below for why "when the cycle started" matters.
  - Day 7 (the big prize): 3 charges of **each** of the three helpers - always exactly 3 credits, one per helper's own slot, each worth 3; if a slot is redirected (see substitution below), that credit's `helperId` changes but its amount never does, so two credits can land on the same helper (showing as two separate "+3" badges, e.g. two Finder icons) rather than silently becoming one "+6" entry.
  - **Snowman substitution:** Snowman is locked until level 10 (`Garden.helpers.isUnlocked`). Any reward that would otherwise credit Snowman before it's unlocked is redirected instead to whichever of finder/random had fewer charges *when the current cycle started*, so nothing is wasted - this applies to day 3's rotation slot, to day 4's "fewest charges" pick (Snowman simply isn't in the eligible set while locked), and to day 7's Snowman slot. One function, `resolveHelperId`, is the single place this substitution happens, used by every reward path above.
  - Charges are always credited through the helpers module (`Garden.helpers.addCharges`) - this file never writes charge storage directly. There is no charge cap anywhere in the game today, so "respect any existing charge cap" is currently a no-op; if one is ever added to `js/helpers.js`, `addCharges` is the one place it would need to clamp, and every credit path here already goes through it.
- **Frozen plan: each cycle's reward *types* are decided once, when it starts, and held fixed for all 7 days.** Day 4's fewest-charges pick and the Snowman-substitution decisions for day 3/day 7 all depend on current charges/unlock state - without freezing them, claiming day 1 (which itself grants a charge) could shift who "looks" fewest by the time day 4 is reached, and the 7-day preview would visibly reshuffle itself mid-cycle (a real bug this fixed: day 3 and day 4's shown helper icons used to swap right after claiming day 1). `computePlan()` runs exactly once per cycle - the moment `nextPositionAfter(position)` would be 1 (never claimed before, or wrapping from day 7) - and its result (`{ day3Helper, day4Helper, day7Helpers }`) is stored in the record's `plan` field and reused for every remaining day of that cycle, in both the real grant (`claim()`) and the popup's preview, regardless of how charges change afterward. Before a cycle has ever started (nothing claimed yet, or right after finishing day 7 with the next cycle not yet begun), there's nothing to freeze, so the preview falls back to a live "best guess right now" - it only locks in the moment day 1 is actually claimed.
- **Position, not streak - missing days pause, they never reset.** The saved record is `{ lastClaimDate, lastSeenDate, position, plan }` (position 0-7, 0 = never claimed). Each claim simply advances `position` by one, wrapping 7 → 1 ("after day 7 the cycle starts again from day 1") - it never depends on how many calendar days passed since the last claim, which is exactly what makes a gap *pause* the cycle instead of resetting it. Claiming when `lastClaimDate` is already today is a no-op (idempotent - a reload or a double tap can never grant twice).
- **Day-diffing is DST-safe:** the gap between two calendar dates is computed from `Date.UTC(y, m, d)` anchors of the date *parts*, never by dividing a millisecond difference between real local `Date` objects - the latter can be off by an hour across a DST boundary (a local day can be 23 or 25 real hours long), while a pure calendar-date UTC anchor has no notion of time-of-day or DST at all.
- **Clock-tampering guard, two-sided.** The record tracks `lastSeenDate` separately from `lastClaimDate` - every status check (not just a claim) bumps `lastSeenDate` forward (monotonic max, `syncSeenDate`) even on a day nothing was claimed. A claim is blocked - granting nothing, leaving the record completely untouched - if today is before `lastSeenDate` (covers the case where the app was *opened* on a later date without claiming, then the clock jumped back) as well as the simpler case of today being before `lastClaimDate` itself. This is only a sanity guard, not real fraud prevention: a purely client-side check can't stop someone from moving the clock forward one day at a time, only catch an actual backwards jump. A real fix needs server time - `Garden.platform.now()` is the one clock entry point everything here goes through, so swapping it for a Yandex SDK server-time call later (roadmap step 8) needs no changes anywhere else.
- **Persist-before-credit:** a claim writes the new record to storage *first*, then credits the reward's charges - so a reload or crash between the two steps can never produce a double claim, though in that narrow window the reward itself could be lost rather than duplicated, which is the intended trade-off.
- **Schema/migration:** `garden.dailyGift` (versioned via `garden.dailyGiftSchemaVersion`) replaced the old streak-based `garden.checkin` key. `Platform.migrateDailyGift()` runs once automatically (idempotent, like `migrateBestTimes`): it carries over the old record's `lastClaimDate` (so updating mid-cycle can never grant a bonus claim on the same calendar day) and best-effort maps the old streak to an initial cycle position, then removes the legacy key. Progress, total score, stars, best times, and helper charges are a completely separate storage prefix and are never touched.
- **Testability:** all date logic flows through the single injectable clock `Garden.platform.now()` (tests override it directly, `Platform.now = () => ...`), so tests simulate arbitrary sequences of days without waiting for real ones; `Platform.saveDailyGift`/`loadDailyGift` store the record with corruption-tolerant loading.
- **UI:** a "Ежедневная награда" button on the main menu (after Settings, before the daily-challenge lock teaser) shows a small dot badge while today's reward is available - no auto-opening popup, the badge is the only nudge. It opens a popup with the 7-day row, a "Забрать" button that disables to "Награда получена" immediately after claiming, and a state line reading "Приходи завтра" whenever nothing is claimable right now (already claimed today, or - rarer - a tampered clock). Claiming pops a short "+N" animation next to the credited helper icon(s) (honoring Reduce Motion). Not shown on the loading screen or inside a level.
- **Design hooks for Codex** (functional only - no styling done here, reusing the existing popup markup from the old check-in step rather than adding new elements, since logic code can't touch `index.html`): `.daily-gift-btn` on the menu button, `.daily-gift-badge` on its unclaimed-today dot, `.daily-popup` on the popup overlay (all three added via `classList.add` in JS, not in the markup), and each of the 7 day cells gets `class="daily-day"`, `data-day="1".."7"`, `data-state="claimed|today|upcoming|paused"`, and `data-special="true"` on days 4 and 7. "paused" is the day right after the one just claimed today - distinct from "upcoming" so a styling pass can visually say "you're mid-cycle, come back tomorrow" rather than "far away." Every day cell also carries a composed `aria-label` (day number, state, and its reward). Each day's reward (and the claim-time "+N" reward pop) is now built from one `.daily-day-reward-item` span **per credit** (icon + its own "+N" right next to it), not one shared icon group with a single trailing number - so a day with multiple credits (day 7) always reads as N separate equal badges, never one bigger merged number. The two old streak-line paragraphs (`#checkinCurrentStreakText`/`#checkinBestStreakText`) are repurposed rather than left dead: the first now shows "День N из 7", the second shows "Приходи завтра" (hidden unless blocked).

## Daily challenge

One special puzzle per calendar date, identical for every player on that date, unlocked once the player reaches level 15 (`Garden.menu.DAILY_CHALLENGE_UNLOCK_LEVEL`/`Garden.dailyChallenge.UNLOCK_LEVEL` - two independent copies of the same constant, same convention as `js/checkin.js`'s own small local rule copies; `tests/daily-challenge.test.js` cross-checks they still agree).

- **One puzzle per date, not per player's own progress.** `js/daily-challenge.js`'s `difficultyLevelForDate(dateKey)` hashes the local date key ("YYYY-MM-DD", from the same single clock entry point everything date-based in this game already uses, `Garden.platform.now()`) down to a "difficulty level" in 15-30, then `buildChallengeLevel(dateKey)` builds an 8×8 board at that difficulty (every level 15+ is already 8×8 - see Level generator above) with a *separate* seed (`generationSeedForDate`, a distinct mix of the same date hash) driving actual generation - so two dates that happen to land on the same difficulty level still always get a different board. The puzzle always starts with nothing pre-placed (`startType: 'none'`, the hardest start) and still respects every existing generator cap (at most 1 pre-placed gingerbread - trivially true at zero givens - and the single-cell-region cap for whichever difficulty level was picked) and the uniqueness guarantee, exactly like a real level.
- **Unlimited attempts until the first win of the day.** Losing an attempt (all 3 candy canes spent) just ends that attempt - Retry rebuilds the exact same puzzle (deterministic by date) for another try, with no limit on how many times. Leaving via the back button costs nothing either way.
- **Shares the same running game instance as normal play, in a separate mode.** Rather than a second parallel game object, `Garden.state.createGame`'s single instance gained `enterChallenge(builderFn, pseudoLevel, boardKey)`/`exitChallenge()`: entering swaps in the challenge's own level-builder and a dedicated board-save key (`'daily-' + dateKey`, so an in-progress attempt can never collide with any real level's saved board) and starts that day's puzzle; leaving (called unconditionally whenever the menu is returned to, a no-op if not currently in challenge mode) reloads the player's real saved progress/board, exactly as if freshly created in normal mode. A `mode` field (`'normal'`/`'challenge'`) rides along on every snapshot so the renderer/menu/input layers can tell which is active.
- **Never touches real progression.** While `mode === 'challenge'`, `js/state.js` skips every per-level/progression side effect a normal win or loss would otherwise trigger: saved progress, the highest-level-reached watermark, best time/best stars per level, the milestone reward, and - critically - **the win streak**, which a challenge win or loss never increments or resets either way. `rating`/`elapsedSeconds`/`levelScore` are still computed and emitted exactly as normal, since the challenge's own reward (below) needs them.
- **Reward on the first win of the day, granted once, idempotently:** 2 charges of whichever helper the player currently has the fewest of (ties favor finder - `pickChallengeRewardHelper`, a small local copy of the same rule `js/checkin.js`/`js/state.js` each keep their own copy of; Snowman is always unlocked by the time level 15 is reachable, so the Snowman-still-locked case other copies handle never actually arises here), the normal points earned this attempt added to the total score once, and the rating (1-3) earned added to a dedicated `challengeStars` counter that's also added directly on top of the existing `totalStars` counter - so "total stars" always reads as "sum of best stars per level + accumulated challenge stars" without re-summing anything. `creditIfFirstWinToday` is the one place any of this is granted: it persists "rewarded today" to storage *first*, then credits the charges/score/stars (same persist-before-credit ordering `js/checkin.js`'s `claim()` uses), so a reload or a double-tap on the win screen re-delivering the same win can never grant it twice.
- **Clock handling identical in style to the daily gift.** "Today" is always the player's local calendar date; a `lastSeenDate` tracked separately from `lastRewardDate` is bumped forward (monotonic max) on every check, even on a day nothing was won, so a device clock that later jumps *backwards* relative to the latest date ever observed is caught and blocks the reward - the same two-sided tampering guard `js/checkin.js`'s `computeClaim` uses, not real fraud prevention (it can't stop someone walking the clock forward a day at a time, only catch an actual backwards jump).
- **Save/migration:** `garden.dailyChallenge` (`{ lastSeenDate, lastRewardDate, challengeStars }`), versioned via `garden.dailyChallengeSchemaVersion` and migrated once, idempotently, by `Platform.migrateDailyChallenge()` - the same "brand-new feature, nothing to migrate FROM" shape `migrateStars`/`migrateAudioSettings` already use, so it only ever has to establish the fresh record once. Progress, total score, best times, stars, helper charges, win streak, daily gift state, and sound settings are all completely separate storage prefixes and are never touched.
- **UI, functional only (no styling done here):** the menu's daily-challenge button (`index.html`'s existing locked-teaser markup, reused rather than replaced) now has three real states via `data-state="locked|available|done"` (`.daily-challenge-btn` on the button, `.daily-challenge-badge` on a JS-created badge shown only while `available`) - `locked` below level 15 (disabled, lock icon, "Откроется на уровне 15"), `available` once unlocked and not yet won today (tappable, "Ежедневное испытание", badge visible), `done` after the first win today (disabled again - no reward on a replay, so replay is simply disabled rather than engineered around deeper in the game - "Выполнено на сегодня"). Tapping it while `available` calls `Garden.dailyChallenge.start(game)` and enters the game screen directly. In the game screen, a `.challenge-banner` label ("Ежедневное испытание") is shown for as long as the attempt is open, built and toggled the same way the existing milestone banner already is. On the win screen, a challenge win repurposes the existing primary button to "В меню" (there's no "next level" for a once-a-day puzzle - `js/input.js` branches on `snapshot.mode`) and shows `.challenge-reward` (the same `.reward-badge`/`helper-reward-icons` markup the milestone reward and win-streak bonus already use, hidden on a replay since `challengeReward` is `null` then) plus "Приходи завтра" (`.challenge-come-back-tomorrow`, reusing the daily gift's own `dailyGiftComeBackTomorrow` i18n string for the exact same phrase rather than duplicating it).
- **Design hooks for Codex** (functional only, as above): `.daily-challenge-btn`/`data-state`/`.daily-challenge-badge` on the menu button; `.challenge-banner` in the game screen; `.challenge-reward`/`.challenge-come-back-tomorrow` on the win screen. None of this needed a new `index.html` element beyond the one `<script src="js/daily-challenge.js">` tag (followed by re-running `tools/stamp-version.ps1`) - every other hook is created in JS and inserted next to existing markup, same convention every prior feature here has used.

Verified by new `tests/daily-challenge.test.js` (134 checks: same date always gives the same difficulty level, a 60-date sample landing on more than one distinct level and always within 15-30, two same-difficulty-level dates still producing different boards via the distinct generation seed, the generated board always respecting the generator caps and having a unique solution, the unlock level matching the menu's own independent copy, unlimited loss-then-retry attempts never touching saved progress/the highest-level watermark/the win streak, `exitChallenge` restoring normal mode and the real level, a genuine win granting the full reward exactly once - charges/points/stars all landing correctly - an idempotent re-handle of the same win snapshot and a same-day replay both granting nothing further, a new calendar day allowing the reward again with a different puzzle, a clock rolled backwards granting nothing, and migration establishing the fresh record while leaving every other kind of saved data - progress, total score, best time, best stars, win streak, daily gift, sound settings, helper charges - completely untouched, twice over to confirm it's idempotent) plus the rest of the Node suite (all green).

## Testing aid: simulating days, streaks, stars, and the daily challenge without waiting

Opening the game with `?debug=1` in the URL enables `window.GardenDebug` (wired in `js/main.js`, gated by `Garden.platform.isDebugEnabled()` - absent entirely without the param, so it can never reach a real player):

- `GardenDebug.advanceDays(n)` - shifts the simulated clock by `n` days (can be negative; repeated calls accumulate). This is the single shared clock (`Garden.platform.now()`) both the daily gift AND the daily challenge read "today" from, so advancing it also changes which puzzle the challenge generates and the menu button's available/done state; level generation for normal levels, timers, etc. are untouched, since nothing else in the game is date-based.
- `GardenDebug.jumpToDay(k)` - jumps straight to cycle day `k` (1-7) being claimable right now, without claiming every day in between.
- `GardenDebug.resetDailyGift()` - resets the daily gift back to "never claimed" (the simulated day offset from `advanceDays` is untouched).
- `GardenDebug.setWinStreak(n)` - sets the win streak directly (e.g. `setWinStreak(4)`, then win one level normally to see the every-5th-win bonus trigger) - skips having to actually win `n` levels in a row first.
- `GardenDebug.setTotalStars(n)` - sets the menu's total-stars counter directly, to check its display (`.menu-total-stars`) without replaying levels for real stars.
- `GardenDebug.resetDailyChallenge()` - resets today's daily-challenge reward back to "not won yet" (and clears any in-progress saved attempt), for re-testing the once-per-day reward repeatedly without waiting for a new day.
- `GardenDebug.setUnlockedLevel(n)` - sets the player's saved progress level directly (e.g. `setUnlockedLevel(15)` to unlock the daily-challenge button), also raising the highest-level-reached watermark to match (so Snowman's own level-10 unlock stays consistent) - bypasses actually climbing there level by level.
- `GardenDebug.state()` - returns `{ today, dailyGift, winStreak, totalStars, progressLevel, dailyChallenge: { lastSeenDate, lastRewardDate, challengeStars, difficultyLevel, doneToday } }` for a quick look at everything simulated/saved right now.

For the daily gift: `GardenDebug.jumpToDay(7); GardenDebug.state();` - re-open the daily gift popup (or call it while already open) to see the result immediately, no reload needed. For the win streak: `GardenDebug.setWinStreak(4)`, then play and win one level for real to see "Серия: 5" and the bonus badge on the win screen. For total stars: `GardenDebug.setTotalStars(42)`, then open/return to the menu to see "★ 42".

## Accessibility

- Every flower bed region must be distinguishable not only by color but also by a subtle pattern (dots, stripes, etc.) drawn in SVG/CSS.
- A settings toggle lets the player turn region patterns on/off — **off by default** (patterns are an accessibility aid, not the normal look).
- A "Reduce motion" setting disables ambient particles and the longer decorative animations (bloom overshoot, pollen sparkles, win-screen sway), and is also honored automatically from the OS-level `prefers-reduced-motion: reduce` media query.
- A "Vibrate on mistake" setting (on by default) triggers a short `navigator.vibrate` pulse on a wrong placement, where supported. Support is feature-detected (`'vibrate' in navigator`), not assumed — browsers that implement it (e.g. Android Chrome) get the real pulse, while browsers that don't (e.g. iOS Safari, which has no `navigator.vibrate` at all) show the toggle disabled with a short explanatory note instead of silently doing nothing; the stored setting's value is unaffected either way.

## Themes

- **Registry (`js/themes.js`).** Two themes, keyed by id: `winter` and `garden`. Each one provides a token map (CSS custom-property overrides), an ordered list of 8 bed colors, a piece-art SVG component, a mascot icon, and i18n keys for the text that differs. A theme is purely visual - it never touches the RNG, generator, solver, or state: level N always has the exact same beds and solution under either theme, only drawn differently (`tests/themes.test.js` guards this directly).
- **Default.** `DEFAULT_THEME_ID = 'winter'` is the one constant that picks the default; changing it to `'garden'` is the only change needed to make garden the default again. The chosen theme is persisted via `platform.saveTheme`/`loadTheme` (corruption-tolerant - an invalid or missing stored value resolves to `DEFAULT_THEME_ID` in `Themes.applyTheme`, not in `platform.js`, since the registry is the one place that knows which ids are valid).
- **Applying a theme.** `Themes.applyTheme(id)` sets `data-theme` on `<html>` and writes the theme's token overrides as inline CSS custom properties on the root element (clearing any previous theme's overrides first). The `:root` block in `css/style.css` is left exactly as the original dark "night garden" look - that's what the garden theme's (empty) token map relies on, which is what keeps "garden theme: exactly today's look" true for free. `render.js`'s `setTheme()` wraps this together with switching the i18n piece-name axis (`I18n.setTheme`) and refreshing everything already drawn with theme-baked content: rule/tutorial text, bed-tracker icons, any already-planted piece SVGs, and the mascot in all its slots (loading/menu/tutorial) (bed *background* colors update for free via the CSS variables, with no explicit refresh needed).
- **Winter theme (light).** A warm cream-to-pale-pink background gradient (no pure white anywhere - off-white/cream tokens throughout) with slow falling snow motes (the same ambient-particle system as garden's pollen, just falling instead of rising, still honoring Reduce motion), a snow drift along the bottom edge and two small snowy fir trees in the lower corners (plain CSS/SVG, `pointer-events: none`, purely decorative); all of it hides automatically in landscape or on a short viewport (`@media (max-height: 700px), (orientation: landscape)`) so it can never shrink the board or overlap controls. A thin candy-cane rim (diagonal red/off-white `repeating-linear-gradient`) frames the board; tiles get a lighter "icy-candy" bevel (brighter highlight, cool blue-grey lower edge, a translucent sheen) on the same geometry/press behavior as today. 8 medium-saturation candy bed colors (mint, strawberry, lemon, grape, blueberry, orange sherbet, lime, bubblegum) were tuned - and are guarded by `tests/themes.test.js` - to stay clearly distinguishable from each other and from the light background. ## Visual style

- **Theme.** Two selectable themes - see the Themes section above for winter (light, default) vs. garden (dark, "night garden", today's original look). Everything below describes the garden theme's tokens/values specifically, which are also the `:root` defaults in `css/style.css`; a dark-green gradient background (no pure white or pure black anywhere in the palette). All colors, radii, shadows, and animation durations/easings are design tokens (CSS custom properties) defined once in `:root`, so the look can be re-themed from one place - which is exactly how the winter theme overrides a subset of them.
- **Bed colors:** 8 muted pastel tones (`--region-0`..`--region-7`), chosen to stay clearly distinguishable from each other against the dark background.
- **Tiles ("candy tile" look):** one uniform gap between every cell — ~6-8px on small boards, scaled down on bigger ones but never below ~3px (`gapForSize()` in `js/render.js`: 8px at size ≤4, 7px at 5, 6px at 6, 4.5px at 7, 3px at 8) — identical whether two neighboring cells share a bed or not; beds are told apart only by color (plus the optional pattern toggle). Cells use a large `border-radius: 24%` (scales automatically with cell size) for a soft, chunky look, plus more volume than a flat tile: a soft lighter top highlight, a ~3px darker lower edge, and a gentle drop shadow (`--tile-highlight`/`--tile-edge`/`--tile-shadow`) — still calm, no harsh contrast. Pressing/dragging a cell reduces that lower edge and shifts the tile down by the matching `--tile-press-shift`, then springs back. Verified an 8×8 board keeps ~44px cells on a 390×844 phone-portrait viewport, comfortably over the 36px minimum tap target.
- **Flowers:** a single reusable "rose spiral" SVG component (`flowerSvgFor(region)` in `js/render.js`) — three rings of pointed petals (6 outer, 5 middle, 4 inner), each ring rotated a bit further than the last, opening outer-to-inner with a small scale+rotate overshoot ("spiral unfurl"). On the board it fills ~78% of its cell (`.cell-mark`) so it reads at a glance even on an 8×8 board; the per-bed tracker icon and win-screen bloom follow the same ~75-78% fill convention at their own sizes. The flower's color is *generated from its bed's own hue* at draw time (`flowerPalette()`: same hue, pushed at least ~40 lightness points lighter or darker — whichever increases contrast against the bed's own lightness — and nudged a little further ring by ring, each stage independently clamped so no ring can ever collapse to pure black/white), not a separate hardcoded palette, so any new bed color automatically gets a flower that contrasts with it. The exact same component renders the flower everywhere one appears: the board, the per-bed tracker row, the tutorial, and a small decorative bloom on the win screen. Once the level is solved, every flower on the board still sways gently in place. X marks use a single dark-ink tone (`--mark-ink`) chosen to stay readable on every bed color; a red disc + bold X (`--mark-wrong`) marks a mistake.
- **Cell feel:** pressing a cell "sinks" it (see Tiles above) and springs back with a slight overshoot; dragging to mark a run of cells sinks each cell in turn as the pointer passes over it; X marks pop in with a short scale animation.
- No fake "fastest player"/leaderboard-percentage banners anywhere on the board or win screen (see Win screen rating below — that rule still holds).
- **Top bar:** back button (left, returns to the main menu) and a settings button (right) frame a centered stack of pills — level number, then score (small leaf icon) — plus three glowing candy-cane lives next to the settings button; a lost life fades and pops exactly as before.
- **Rules bar:** the three rule cards show inline on levels 1-5; from level 6 on they collapse behind a small "?" button that opens them in a dismissible popup instead, keeping the board bigger on larger levels.
- **Helpers row:** three round placeholder-icon buttons below the board (Finder, Random, Snowman), each with a charge-count badge - disabled/locked states as described under Helpers above.
- **Settings popup:** patterns, reduce motion, and vibration toggles plus a "Replay tutorial" button, opened from the top-bar settings button.
- **Tutorial:** the dimming/backdrop uses the same dark-green scrim as the rest of the UI; the one interactive cell gets a soft glowing ring instead of a hard highlight; hints are shown in a speech bubble anchored to a small ladybug mascot (SVG) rather than a bare box.
- **Ambient particles:** a handful of slow-drifting pollen/firefly motes rendered as small glowing dots behind the UI (plain CSS animation on ~10 tiny absolutely-positioned elements — no canvas, no blur over large areas, so it stays cheap on weak phones). Disabled entirely under "Reduce motion" or `prefers-reduced-motion`.
- Calm, cozy tone — not stressful despite the lives mechanic.
- CSS/SVG graphics only; no image/bitmap assets.

## Sound and music

Everything audible is synthesized at runtime with the Web Audio API (`js/audio.js`) - no audio files, no network requests, nothing recorded or borrowed from an existing song/game. Browser-only, but written so a fake `AudioContext`/`document`/`window` can be swapped in for the gating logic (`tests/audio.test.js`); render.js/input.js/checkin.js/menu.js/tutorial.js's actual event wiring is only statically checked (`tests/audio-hooks.test.js`), the same lightweight textual-scan technique `tests/index-html-version.test.js` already uses - the real sound still needs a real-browser/device pass, same as every other DOM-only module in this project.

- **First-gesture unlock.** The `AudioContext` is created (and, on a later suspend, re-resumed) only from inside a real user gesture (`pointerdown`/`touchend`/`keydown`, document-level, **capture phase** so it always runs before the board's own bubble-phase tap handler on that same first tap) - required by iOS Safari/Yandex Browser, which otherwise leave a context permanently suspended. `playEffect()` before that first gesture is a silent no-op, never a crash or a queued sound.
- **Mixing graph.** `masterGain -> DynamicsCompressorNode -> destination` (a gentle limiter so layered effects/notes can never clip). Effects connect straight into `masterGain`; music goes through its own `musicBus` (overall music volume + the on/off fade) feeding two crossfade-weight gains, one per track. A hard cap (16) on simultaneous synthesized voices protects weak phones; every voice disconnects all of its nodes the instant it ends (`osc.onended`), so a long session never accumulates dead nodes.
- **Effects** (`Garden.audio.EFFECT_IDS`): short (<1s), soft, cozy bell/marimba/wood timbres, never harsh - `tap` (generic button/toggle click), `placeFlower` (two-note soft chime), `placeCross` (a light, quick wooden tick), `mistake` (a low, soft bonk - never alarming), `helperUse` (a quick ascending sparkle cluster), `win` (a rising bell arpeggio, with two extra bright notes layered in for a 3-star finish), `lose` (a gentle falling phrase), `reward` (a sparkly ascending jingle, shared by the milestone reward, the win-streak bonus, and the daily-gift claim), `milestoneStart` (a small triangle-timbre fanfare). None of this lives in game logic - every hook is an additive `Garden.audio.playEffect(id)` call at an existing DOM-rendering site, keyed off a snapshot field or cell-state transition that already existed:
  - `js/render.js`: `placeFlower`/`placeCross` on the exact cell-state transition that already drives the bloom/mark-pop animation in `syncCells`; `mistake` vs. `lose` on `snapshot.mistake` (picking `lose` on the exact tick a mistake also sets `status: 'lost'`); `win` (with the star rating) and `reward` (milestone reward badge, win-streak bonus badge) in `showWinOverlay`; `milestoneStart` the moment a freshly-entered level's `levelKind` is `'milestone'`.
  - `js/input.js`: a generic `tap` tick wired to every plain chrome button/toggle (back, settings, rules, theme, retry/next-level, patterns/reduce-motion/vibration) - never the board itself, which already gets its own effects above; `helperUse` right after any successful `game.useHelper(id)`.
  - `js/checkin.js`: `tap` on opening/closing the daily-gift popup, `reward` on an actual claim.
  - `js/menu.js`: `tap` on Play/How-to-play/Settings.
  - `js/tutorial.js`: the same `placeFlower`/`placeCross` feedback as the real board, `tap` on the final "Got it!" button. (The tutorial's own 4x4 practice board doesn't go through `js/state.js` at all, so this is a separate, parallel hook - deliberately kept in sync by hand.)
- **Music.** Two short, calm, original, procedurally-generated loops (a sparse major/minor-pentatonic bell melody over a soft sustained two-note pad, ~60-76 BPM-equivalent note spacing, built from a small per-step scale-degree pattern rather than a giant hand-written frequency table) - one for menu/loading/tutorial, one for gameplay, switched via `Garden.audio.setMusicTrack('menu' | 'game' | null)` with a ~1.4s crossfade (the outgoing track's scheduler only actually stops once its fade-out finishes). A look-ahead scheduler (checks every 150ms, always keeps ~0.6s of notes already scheduled) keeps the loop seamless even if the main thread is briefly busy. Music sits well below effects in volume. Wired in `js/main.js`: `'game'` on entering a level, `'menu'` on returning to the menu and at startup, and swapped to `'menu'` for the duration of the tutorial (restored to whichever screen is actually showing once the tutorial finishes), regardless of whether the tutorial was reached from the menu or from "Replay tutorial" mid-level.
- **Pause rules.** Suspends the *entire* `AudioContext` (effects and music together) on `visibilitychange` (hidden), `pagehide`, and window `blur`; resumes on the matching visible/`pageshow`/`focus` event - tracked as a set of overlapping reasons (mirrors `js/state.js`'s own `pauseTimer`/`resumeTimer`), so it only actually resumes once every reason has cleared. A separate `Garden.audio.setExternalMute(key, true|false)` stacks independently on top of that - a future Yandex SDK hook (roadmap step 8): e.g. `setExternalMute('ad', true)` right before a rewarded/interstitial ad, `false` right after, with no changes needed anywhere else.
- **Settings.** Two independent, persisted booleans, both default **on**: `garden.sfxEnabled`/`garden.musicEnabled` (`js/platform.js`, migrated once via `migrateAudioSettings()`/`garden.audioSchemaVersion` the same idempotent "establish once" shape `migrateStars()` already uses - there's no earlier sound feature to migrate data from, and it never touches progress/score/stars/best times/charges/win streak/daily gift). Toggling effects off silences new ones immediately (in-flight short effects just finish naturally); toggling music off fades it out over ~0.5s and then actually stops the scheduler (not just mutes it), so a disabled player's session never keeps synthesizing silent notes in the background. The Settings popup's markup lives in `index.html`, which only Codex edits for presentation - so `Garden.audio.createSettingsRows(dom)` builds the two rows in JS instead (inserted right before the existing "Replay tutorial" button), reusing the exact `.settings-row`/`.toggle-switch`/`.toggle-knob` markup the other toggles already use so existing CSS applies for free. Stable hooks for Codex's styling pass: `.setting-sfx` / `.setting-music` on each row, labels "Звуковые эффекты"/"Музыка" (EN: "Sound effects"/"Music") via i18n.
- **Verified here:** `tests/audio.test.js` (fake `AudioContext`/`document`/`window` - no audio before the first gesture, settings persistence + migration leaving unrelated keys untouched, suspend/resume on hidden/visible/blur/focus/pagehide including overlapping reasons, the external-mute API stacking with a real pause reason, an unknown effect id and an unknown music-track name both being safe no-ops, the voice cap, and that ending a voice disconnects its nodes and frees the slot for reuse) and `tests/audio-hooks.test.js` (every expected `playEffect`/`setMusicTrack`/lifecycle call is textually present in the right file, and every id `js/audio.js` defines is referenced by at least one hook) plus the rest of the Node suite (unaffected). **Not verifiable here, needs a real device/browser:** actually hearing any of this - whether the timbres read as "cozy" rather than harsh, whether the loop is actually seamless, whether iOS Safari/Yandex Browser's first-gesture unlock behaves as expected on a real iPhone, and whether backgrounding/returning to the app (not just firing the DOM events a desktop browser fires) truly pauses/resumes cleanly.

## Release routine

Root cause of a real bug: `index.html`'s `<link>`/`<script>` tags had no cache-busting token, so a phone that had already cached an old `js/render.js` (etc.) under that exact URL could keep serving it after a new deploy, even though brand-new CSS files (never-before-seen URLs) always came through fresh - no build step or server-side header control exists (GitHub Pages) to fix this any other way.

**After merging a design pass into `main`, and right before the final commit/push of a release:**

1. Run `tools\stamp-version.ps1` (Windows PowerShell 5.1, no dependencies) from the repo root:
   ```
   powershell -ExecutionPolicy Bypass -File tools\stamp-version.ps1
   ```
   This stamps every LOCAL `<link rel="stylesheet" href="...">` and `<script src="...">` tag in `index.html` with the same `?v=<yyyyMMdd-HHmm>` token (replacing any existing one), so every asset URL changes on every release and can never be served stale. External URLs (if any are ever added, e.g. a Yandex SDK script tag) are left untouched.
2. `tools\stamp-version.ps1 -Check` verifies every such tag already has a token and that all tokens match, without modifying the file - exits non-zero if anything is missing/inconsistent (`tests/index-html-version.test.js` runs the same check in the regular Node suite).
3. Commit the stamped `index.html` and push.

**Known gap, flagged for Codex, not fixed here** (these aren't `<link>`/`<script>` tags in `index.html`, so the script doesn't touch them, and they live in `css/`/`fonts/` which logic code doesn't edit): `css/style.css`'s `@font-face` (`url('../fonts/Comfortaa.ttf')`) and three `url(...)` references to standalone SVGs sitting directly in `css/` (`css/winter-cane-full.svg`, `css/winter-cane-spent.svg`, `css/winter-gift-bow.svg`, used by `css/winter-ornaments.css`/`css/daily-gift.css`) have no cache-busting of their own. In practice this is lower-risk than the JS/CSS bug above - CSS itself is now always versioned, and browsers generally re-resolve a stylesheet's own `url(...)` references whenever the stylesheet itself is re-fetched - but it's worth Codex adding a matching version query (or accepting the same small staleness risk) if this ever causes a visible symptom (a swapped-out SVG/font not updating).

## Yandex Games SDK integration

`js/yandex.js` is the ONLY module allowed to touch `window.YaGames` - every other module (including `js/platform.js`) talks exclusively to `Garden.yandex`, exactly like `js/audio.js`/`js/platform.js` already isolate Web Audio/localStorage behind their own small APIs. It holds two backends behind one identical interface - a **real** backend (a thin, defensively-wrapped adapter around the actual SDK methods) and a **mock** twin - and picks between them once, at boot: the mock is used whenever `window.YaGames` is absent (GitHub Pages, a local file open) or `?mock=1` is in the URL (forces the mock even when the real SDK IS present, e.g. to test it inside a real Yandex Games preview iframe). If the real SDK is present but its own `init()` rejects (offline, an SDK-side error), it falls back to the mock automatically rather than leaving the game stuck - the menu is never blocked waiting on the SDK, per the platform constraints above.

**Lifecycle.** `Garden.yandex.init()` starts the handshake as early as possible (before `DOMContentLoaded`, in `js/main.js`). `platform.gameReady()` (called once the menu is interactive, same call site as before) now also calls `Garden.yandex.ready()` - which queues the actual `features.LoadingAPI.ready()` call if the SDK's own `init()` promise hasn't resolved yet, rather than dropping it, since Yandex Games itself waits on this to dismiss its own loading screen. `Garden.yandex.gameplayStart()`/`gameplayStop()` wrap `features.GameplayAPI` and are idempotent (a second `start()`/`stop()` while already in that state is a no-op), so every call site can just call them unconditionally: `gameplayStart()` on entering a level or challenge; `gameplayStop()` on win, lose, opening Settings or "How to play"/tutorial, opening a rewarded ad, and returning to the menu. `Garden.yandex.onPauseResume({onPause, onResume})` subscribes to the platform's own `game_api_pause`/`game_api_resume` events (best-effort - the exact subscription shape couldn't be confirmed without a live SDK session, see Open questions below) and pauses/resumes the same active-play timer and audio mute every other pause reason already uses.

**Rewarded ads (helper refill).** A helper button with 0 charges (and already unlocked) shows an ad-tap state instead of its normal disabled-at-zero look: `Garden.helpers.needsAd(id)` is true, `js/state.js`'s snapshot carries it as `helpers[id].needsAd`, and `js/render.js` sets `data-ad="true"` on the button plus an empty `.helper-ad-icon` span inside it (Codex draws the glyph; the existing charge badge shows "+1" via i18n instead of "0" in this state). Tapping it (`js/input.js`) goes straight to `Garden.yandex.showRewardedAd({onOpen, onRewarded, onClose, onError})` - no confirmation dialog - after pausing the timer, stopping the GameplayAPI session, and muting via `Garden.audio.setExternalMute('ad', true)`; the charge is granted **only** inside `onRewarded` (idempotent even if the backend somehow fires it twice), and the helper is actually used (`game.useHelper(id)`) only after `onClose` reports a genuine reward for that session. `onError`/no ad available grants nothing and shows a short, non-blocking `.ad-message` (auto-hiding) via a new `adUnavailableMessage` i18n string; either way, `onClose`/`onError` always unmute, resume the timer, and resume the GameplayAPI session. `Yandex.showRewardedAd()` itself refuses a second concurrent call (returns `false`, touches nothing) and `js/input.js` additionally blocks all board/chrome input for the whole time an ad is open (`inputBlocked`) - belt-and-suspenders against a double tap.

**Cloud saves.** `Garden.yandex.cloudSaveInit(onMerged)` runs once at boot, well after the menu is already interactive (never blocks it): it reads the cloud snapshot via `player.getData()` (non-forced `getPlayer()`, works for an unauthorized player too), re-reads the LOCAL snapshot fresh at that exact moment (minimizing, though not eliminating, the race against a local write that happens during the fetch's own round trip), merges the two, writes the result back to `localStorage` if anything changed, and immediately pushes the reconciled snapshot back up so both sides agree. `localStorage` (`js/platform.js`) stays the primary, always-available fast copy; the cloud is synced on top of it.

What's synced (and what deliberately isn't): the board-in-progress is **never** part of this payload (resuming an exact mid-level board across devices was out of scope for this pass); `patternsEnabled`/`reduceMotion`/`vibrationEnabled`/`tutorialDone` stay local-only on purpose (device-specific/accessibility prefs, not something one device should push onto another).

Merge policy (`Garden.yandex.mergeSnapshots`, pure and unit-tested in `tests/yandex.test.js`):
- **Max, never regress:** current level progress, highest level ever reached, total score, per-level best stars, best-ever win streak, and accumulated daily-challenge stars.
- **Min:** per-level best time.
- **Take the whole value from whichever device wrote most recently:** helper charges, the LIVE win-streak counter (which can legitimately drop to 0 on a loss, so max would be wrong for it), the rest of the daily-gift record (cycle position, frozen week plan), the rest of the daily-challenge record, and sound/theme settings. "Most recently" is one shared `garden.savedAt` timestamp (`js/platform.js`, a real `Date.now()`, bumped by every setter in this group) - a deliberate simplification: one combined timestamp for this whole group rather than a separate one per field, since in normal play they all change together anyway.
- **Extra guard on top of the above:** a daily-gift claim date / daily-challenge reward date can never regress across a merge, even on the side that loses the `savedAt` comparison - whichever of the two dates is chronologically later always wins for that one field. This is the one case where losing the `savedAt`-side pick would let the exact same day's reward be claimed twice across two devices; `tests/yandex.test.js` covers this directly (a merged "already claimed today on both sides" record can never be claimed a third time via `Garden.checkin.computeClaim`).
- `totalStars` itself is never merged directly (it isn't in the list above at all) - it's **recomputed from scratch** after the merge, as sum(merged per-level best stars) + merged `challengeStars`, via `Platform.recomputeTotalStars()`, so it can never drift from that already-documented invariant (see "Total stars" above) or get double-counted against the per-level deltas `saveBestStars` normally tracks.

Writes are debounced (`CLOUD_SAVE_DEBOUNCE_MS`, ~1.5s, coalescing a burst of rapid writes into one `player.setData(data, true)` call) but flushed immediately (bypassing the debounce) on `visibilitychange` going hidden and on `pagehide`, since the page could be frozen or killed right after either. Every meaningful local write (level end, helper use, a reward claim, a settings change) already routes through one of `js/platform.js`'s own setters, which call a small `notifyCloudDirty()`/`touchSavedAt()` hook - so nothing extra needed to be sprinkled across `js/state.js`/`js/helpers.js`/`js/checkin.js`/`js/daily-challenge.js` to trigger a save.

**Server time.** `Garden.platform.now()` - the single clock entry point every date-based feature (daily gift, daily challenge) already went through - now prefers the SDK's `serverTime()` (cached as an offset from the device clock, refreshed once at init via `Garden.yandex.refreshServerTimeOffset()`) over the plain device clock, falling back to the device clock if the SDK has none or it throws. The existing `?debug=1` day-offset still applies on top of whichever base clock was picked, and the existing backwards-clock tamper guards in `js/checkin.js`/`js/daily-challenge.js` need no changes at all, since they only ever consume `Platform.now()`.

**Leaderboard.** Technical name `"points"` (`Garden.yandex.LEADERBOARD_NAME`) - score = total points, submitted (`Yandex.submitScore`) after every level win and every daily-challenge win, only if the player is authorized and `isAvailableMethod('leaderboards.setScore')` says so, throttled to at most one request per second with only the latest queued value actually sent (a leading-edge-if-idle, trailing-edge-coalesced throttle). A `.leaderboard-btn` menu button and a `.leaderboard-popup` (rows: `.leaderboard-row`, own row highlighted `.leaderboard-me`, `.leaderboard-empty` when there's nothing to show) are built entirely in JS (`Garden.yandex.createLeaderboardScreen`) - index.html had no slot for either and this task's rules only allowed adding one new script tag there. Tapping the button when not authorized calls `ysdk.auth.openAuthDialog()` once, then re-reads the player; declining just closes the popup with no nagging anywhere else in the game, and a later tap on the same button will always prompt again (never permanently blocked by an earlier decline) - covered directly in `tests/yandex.test.js`.

**"You beat N%" on the win screen.** Shown only if it can be computed from real SDK data (own rank + total number of entries) - `Garden.yandex.getLeaderboardTotalEntries()` always returns `null` in real mode, since no documented real-SDK call for "total entries on a leaderboard" could be found (see Open questions below), so the line (`.win-beat-percent`, `Yandex.fetchBeatPercentForWinScreen`) never actually renders in real mode today - not a bug, the deliberate "don't fake it" behavior. The mock backend returns a fixed fake total purely so the line has something to show while developing/testing the UI, clearly commented as mock-only in `js/yandex.js`.

**Mock mode & debug aids.** `?mock=1` forces the mock backend even when the real SDK is present. The mock's rewarded ad is a 2-second delay that always succeeds (reward + close); `?debug=1`'s `window.GardenDebug` gained `simulateAdError()` to force the *next* rewarded ad to fail instead, for testing the ad-unavailable message on demand. The mock's "cloud" is backed by its own separate `localStorage` key (`garden.mockCloudData`) and its leaderboard/auth are clearly-fake dev-only data (see `js/yandex.js`'s own comments).

**Open questions for the real Yandex Games Console/draft** (couldn't be confirmed without a live SDK session - flagged rather than guessed silently):
- The exact subscription shape for `game_api_pause`/`game_api_resume` (`Garden.yandex`'s real backend assumes `ysdk.on(eventName, cb)`) - worth confirming once the draft is live; if wrong, pause/resume events simply never fire (fails safe, doesn't throw).
- Whether the real `leaderboards.getEntries()` response's "player not present" case actually surfaces as a missing/non-numeric `userRank`, as assumed here.
- Whether the SDK ever exposes a real "total entries on this leaderboard" figure anywhere - if it does, `getLeaderboardTotalEntries()` in the real backend is the one place to wire it up for the "beat N%" line to finally render for real players.
